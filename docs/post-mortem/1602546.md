# AB#1602546

_Status: living document, updated as work continues. Published to Discussions: [#475](https://github.com/AlaskaAirlines/AuroDocsSite/discussions/475)._

## Executive Summary

The Auro documentation site had an Icons page, but two other collections that ship in the
same icon library were invisible to anyone browsing the site: the airline **tail** marks
(Alaska and its partner carriers) and the newer **pictogram** illustrations. Teams used these
assets but couldn't discover them on the site. This work adds two new browsable pages — **Tails**
and **Pictograms** — reachable from the same navigation as Icons, closing that discoverability gap.

Ticket: [AB#1602546](https://itsals.visualstudio.com/E_Retain_Content/_workitems/edit/1602546)

## The Problem

The docs site's Icons page only showed general-purpose UI icons. The airline tail logos and the
illustrative pictograms — both part of the official icon library — never appeared anywhere on the
site, so people couldn't tell they existed or see what was available. The ask was to surface them
in a dedicated, browsable place alongside Icons. Midway through, the decision (with design/lead
input) was to give tails and pictograms **their own separate pages** rather than one combined page,
since they are distinct asset types with different use cases.

## Root Cause

Not a defect — a coverage gap in the docs-site build tooling plus a rendering-size issue:

- **Discoverability gap:** `scripts/build-icon-lib.js` auto-generates the icon gallery by scanning
  only `node_modules/@alaskaairux/icons/dist/icons`. Tails live in a sibling tree
  (`dist/logos/tail-*.svg`) and pictograms in another (`dist/pictograms/`), so neither was ever
  read or rendered.
- **Stale dependency:** the site had `@alaskaairux/icons@5.25.0` installed; the pictogram collection
  (`dist/pictograms/`, plus `src/data/pictograms.json`) was introduced upstream in **5.26.0**. So
  pictograms were not even present locally until the dependency was bumped.
- **Sizing bug (interim):** tail/pictogram SVGs carry an inline `style="min-width:100%;height:auto"`,
  whereas UI-icon glyphs use a CSS-variable-based size. The gallery CSS sized icons by overriding those
  variables, which had no effect on the tails' inline `min-width:100%`, so tails overflowed their demo
  boxes. (Superseded by the `<img>` rewrite below, which doesn't carry that inline style.)
- **ID-collision bug (the serious one):** many tail SVGs use short internal ids (`A`/`B`/`C`) for
  `<use href="#B">`, `mask="url(#C)"`, and `filter="url(#A)"`. Rendering them via SVGR's `?react`
  **inlines all 50 into one DOM**, where those ids are document-global — 10 tails share `id="A"` and
  37/50 use `url(#…)` references. Only the first occurrence wins, so every tail after the first
  retargeted to the wrong defs and lost its fin body (e.g. Cathay showed only a floating teal mark).
  SVGO (which could disambiguate via `prefixIds`) was not running — `svgr()` had no options and
  `vite-plugin-svgr@4.5.0` doesn't bundle the svgo plugin. Standalone `<img>` avoids this because each
  SVG is its own document; the general UI icons were unaffected (their ids are per-icon namespaced and
  used only for a11y).

## The Fix

- **Dependency:** bump `@alaskaairux/icons` `^5.25.0` → `^5.27.0` (brings in `dist/pictograms/`, which shipped upstream in 5.26.0).
- **Build tooling** (`scripts/build-icon-lib.js`): added a reusable `buildSvgList({ dir, match, label,
  exportName, outFile, wrapperClass })` that scans a dist folder for `.svg` files and emits a gallery
  component. It generates two files: `tailList.js` (from `dist/logos/tail-*.svg`, 50 tails) and
  `pictogramList.js` (from `dist/pictograms/*.svg`, currently 1). Both are tagged
  `className="graphicList"` for scoped CSS. The Icons/deprecated generation is untouched.
- **Rendering as `<img>` (id-collision fix):** tails/pictograms are rendered as plain `<img src>`
  rather than SVGR `?react` inline components — new `buildUrlImports`/`buildImgElements` helpers in
  `scripts/utils.js` emit default URL imports (`import Tail from '…/tail-CX.svg'`) and `<img>` markup.
  Each SVG stays its own document (Vite copies it to a hashed asset), so internal ids can't collide.
  The icons gallery keeps `buildImports`/`buildElements` + `?react` (where inline + `currentColor`
  matter). This matches how the upstream Icons repo renders these static brand marks.
- **Pages & routing:** new `src/content/dynamic/icons/tails.js` (`/tails`) and `pictograms.js`
  (`/pictograms`), each mirroring the Icons page; routes added in `src/App.js`.
- **Navigation:** the global sidenav (`src/components/side-nav.js`) collapses to a single
  **"Iconography"** entry (routing to `/icons`) with `activeRoutes: ['/icons','/tails','/pictograms']`;
  the shared tab strip (`src/content/dynamic/icons/nav.js`) gained **Tails** and **Pictograms** tabs so
  the three cross-link. Sidenav active state now derives from `useLocation()` so it highlights on
  load and across all three sub-pages.
- **Visual cleanup:** removed the header banner image from `icons.js`, `tails.js`, and `pictograms.js`.
- **Sizing:** scoped CSS in `src/sass/App.scss` — `.graphicList .iconsWrapper img` constrains each
  graphic (`max-width:100%`, `max-height` 100px / 120px at larger breakpoints) so it scales to its
  aspect ratio and fits its demo box. (Under `<img>` there's no inline `min-width:100%` to override,
  so the earlier `!important` rule was dropped.)
- **Tests:** stood up **Vitest 3** (`vitest.config.js`) reusing the app's Vite pipeline so `?react`
  svgr imports and `~`/`ROOT` aliases resolve; `tailsAndPictograms.test.js` asserts both galleries
  render (50 tail `<img>`s incl. `tail-AS`/`tail-HA`; the `elbow-room` pictogram). `package.json` `test`
  now runs `vitest run` with a `pretest` that regenerates the gitignored lists; the two generated
  lists are gitignored to match the existing `iconList.js` pattern.

## Why This Works

- The generator emits the exact same `?react`-imported SVG + `.iconsWrapper` markup the Icons page
  already uses, so tails/pictograms inherit the proven gallery layout with no new rendering path.
- Keeping tails and pictograms as **separate generated lists** means splitting or growing either
  collection later needs no tooling change — the icon library itself documents that adding pictograms
  requires "no pipeline changes."
- The sizing override was verified against real output: the production bundle shows the 50 tails
  rendering with inline `minWidth:"100%"` (vs `minWidth:"var(--auro-size-lg…)"` for UI icons),
  confirming the `!important` override targets a genuine inline style rather than guesswork.
- The single "Iconography" sidenav entry keeps the nav uncluttered while the tab strip preserves
  discoverability of all three collections.

## Outcome

The docs site now has dedicated, browsable **Tails** and **Pictograms** pages alongside Icons, all
reachable from one "Iconography" spot in the site navigation. Every airline tail mark and every
available pictogram is listed and correctly sized within its preview tile. The existing Icons gallery
is unchanged. Automated tests were added and pass, and a full production build succeeds.

## Follow-up (2026-08-31): tab-strip divergence

After the initial ship, the **Tails** and **Pictograms** tabs disappeared whenever the
**Install** or **Ways to use** tab was active. This was not a runtime conditional — it was a
**duplicated tab list that drifted**. The iconography section has two page-rendering pipelines,
each with its own copy of the tab strip:

- **Hand-authored gallery pages** (`icons.js`, `tails.js`, `pictograms.js`, `guidelines.js`,
  `deprecatedIcons.js`) render content directly in JSX and import a standalone `<Nav />`
  component from `src/content/dynamic/icons/nav.js`.
- **Markdown-driven pages** (`install.js`, `ways-to-use.js`) are thin subclasses of the
  site-wide markdown base class (`renderComponentPage.js`, used by ~138 pages) via an
  icons-specific override, `renderIconsPage.js`, whose `renderNav()` method held a *second*
  hardcoded copy of the tab list.

When this ticket added the Tails/Pictograms tabs, only `nav.js` was updated; the copy in
`renderIconsPage.js` was missed, so the two markdown pages showed a five-tab strip while the
rest showed seven.

**Fix (de-duplication, not a second patch):** `nav.js` is now the single source of truth.
`renderIconsPage.js` `renderNav()` was reduced to `return <Nav />;` — the duplicated `<NavLink>`
list, the `<LinkIcons>` block, and the redundant `showVersion()` method were deleted, along with
the now-unused `NavLink`/`LinkIcons`/`packageJson` imports. All seven iconography pages now render
one tab definition and can no longer drift. Verified: `npm test` passes (2/2).

**Learning:** the original implementation patched the tab list in one of two copies. The durable
fix was to collapse the copies, not to add the tabs to the second one — duplicated nav definitions
across two rendering pipelines are the root cause, and leaving both in place would have re-created
the drift on the next tab change.

### Open question: supporting pages for Tails/Pictograms

The shared **Install / Design guidelines / Ways to use** tabs now render alongside Tails and
Pictograms, but their *content* is UI-icon-specific and in places does not apply to the branded
marks:

- **Install** (`@aurodesignsystem/auro-icon` readme) — genuinely shared: tails and pictograms
  ship in the *same* `@alaskaairux/icons` npm package (`dist/logos/`, `dist/pictograms/`).
- **Design guidelines** (`guidelines.md`) — UI-icon-only (20px grid, 1.5px stroke, `currentColor`
  recoloring, 16/24/32 sizes); explicitly defers larger imagery to an "Illustrations" page.
- **Ways to use** (`ways-to-use.md`) — describes the `auro-icon` element and recoloring via
  `currentColor`; tails/pictograms are static, branded, rendered as `<img>` and are **not**
  recolored, so this guidance is misleading for them.

Initial recommendation was to *not* create a parallel set of supporting pages per collection.
Investigating further surfaced a deeper, more important problem than the missing tabs: the
icon-family pages source their prose from **three inconsistent places**, and the library already
ships documentation the site never adopted.

**Content-sourcing map (as-is):**

| Page | Prose source | Notes |
| --- | --- | --- |
| Icons / Tails / Pictograms / Deprecated | hardcoded JSX in AuroDocsSite | galleries are generated from the installed package |
| Ways to use | `@alaskaairux/icons/docs/ways-to-use.md` (**Icons repo**) | icon-only; no tails/pictograms |
| Design guidelines | local `guidelines.md` (**AuroDocsSite**) | UI-icon-only (20px grid, stroke, `currentColor`) |
| Install | `@aurodesignsystem/auro-icon/readme.md` (**auro-icon repo**) | a third repo |

**Key finding:** `docs/pictograms.md` already exists in the Icons repo (authored under a *separate*
ticket, AB#1372704) and is **shipped upstream in 5.26.0 and present in the installed
`@alaskaairux/icons@5.27.0` package** — i.e.
importable *today* exactly like `ways-to-use.md`. The tails/pictograms pages simply weren't wired
to it and use hardcoded copy instead. `docs/tails.md` does **not** exist and must be authored.

**Resolution (decided with lead):** commit to a single source of truth — the **Icons library owns
all icon-family prose as markdown** (`icons.md`, `tails.md`, `pictograms.md`, plus the shared
install/guidelines/ways-to-use/deprecated topics, each covering all three collections), and
AuroDocsSite renders that library-owned markdown (as `ways-to-use.js` already does). The generated
galleries stay in AuroDocsSite — only prose moves to markdown. This supersedes the "don't
duplicate pages" recommendation: the fix isn't per-collection pages, it's centralizing the prose.

This is tracked as a follow-up user story, **AB#1634760** (filed against the Icons repo, tagged
`Refinement`), which also captures the cross-repo coordination and the install-content relocation
out of the auro-icon readme. The tab-strip de-duplication above is the immediate fix on this
branch; AB#1634760 is the durable content-architecture work.

## Learnings

- When a docs gallery is auto-generated, "it's not on the site" often means "the generator doesn't
  scan that directory," not "the asset doesn't exist." Check the build script's source path first.
- Verify the **installed** dependency version, not just the declared range — the pictogram collection
  existed upstream (5.26.0) but the site was pinned to 5.25.0, which initially looked like "pictograms
  don't exist."
- Inline SVG styles win over stylesheet rules; the icon library sizes UI glyphs via CSS variables but
  ships tails/pictograms with inline `min-width:100%`. Overriding requires `!important` (or a scoped
  container class), which is justified here because it targets a real inline style.
- This repo puts JSX in `.js` files; Vitest 4's Rolldown parser rejects that, so Vitest 3 (esbuild)
  is the compatible choice. Reusing `vite.config.js` gives tests the svgr/alias pipeline for free.
- Generated artifacts are gitignored here (like `iconList.js`); any test importing them must
  regenerate them first (a `pretest` hook) so CI works from a clean checkout.
- **Inlining SVGs with short, shared internal ids (masks/filters/uses) into one DOM breaks all but
  the first instance** — SVG ids are document-global. For static, non-themed brand art, `<img>`
  (one document per file) is the correct, durable rendering choice; reserve inline `?react` SVGs for
  glyphs that need `currentColor`/CSS theming. If inline is required, enable SVGO `prefixIds` with a
  per-file prefix.
- The Icons repo's own demo rendered these tails correctly with `<img>` on the same background —
  comparing against the upstream source of truth pinpointed the render-mechanism difference fast.

## Iterations That Didn't Work

- **One combined "Tails and Pictograms" page** — initially built as a single page with one combined
  list (`tailsAndPictogramsList.js`). The lead requested separate pages, so it was refactored into two
  generated lists and two page components.
- **Three separate sidenav entries** (Icons, Tails, Pictograms) — cluttered the nav; collapsed to a
  single "Iconography" entry, relying on the tab strip for sub-navigation.
- **Initial "no pictograms exist" assessment** — incorrect; pictograms shipped in icons 5.26.0 while
  the site had 5.25.0 installed. Corrected by bumping the dependency.
- **Page-level "Tails" heading duplicated the generated section heading**, and a large header banner
  sat atop each page — both removed in favor of a concise Overview intro.
- **Vitest 4** — failed to parse JSX-in-`.js` (Rolldown parser); downgraded to Vitest 3.
- **Inline SVGR (`?react`) rendering of tails** — the first implementation inlined all 50 tail SVGs
  into one DOM, which collapsed their shared internal ids (`A`/`B`/`C`) and rendered every tail after
  the first broken (fin body missing). Replaced with `<img>`-based rendering (per-file document
  isolation). Considered but rejected: enabling SVGO `prefixIds` in the SVGR config — it works but is
  global to every `?react` SVG and relies on the prefix staying unique per file; `<img>` is the right
  tool for static, non-themed brand art.
