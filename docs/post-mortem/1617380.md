# AB#1617380

## Executive Summary

The Auro documentation site's **dialog** pages now use the same navigation layout as the FormKit component pages, so visitors get a consistent, predictable way to move through the docs. Previously the dialog docs had a flat set of tabs that didn't match the grouped "Overview / Code / Design / Accessibility / Releases" structure used elsewhere. Alongside the navigation work, the dialog component reference was moved up to its latest published release and a token dependency was aligned so the site builds cleanly.

Ticket: [AB#1617380](https://itsals.visualstudio.com/E_Retain_Content/_workitems/edit/1617380)

## The Problem

The documentation site presents each component through a set of navigation tabs. The FormKit component pages use a grouped navigation — a top row of primary tabs (Overview, Code, Design, Accessibility, Releases) with a contextual second row of sub-tabs — while the dialog pages used an older, flat tab layout. This inconsistency made the dialog documentation feel different from the rest of the site and gave visitors a less predictable browsing experience. The ticket also called for the site to reference the latest released component versions so the examples people read and try match what actually ships.

## Root Cause

The docs site renders component pages through two base classes:

- `src/functions/renderComponentPage.js` — used by ~40 standalone components (including dialog). Its `renderNav()` produced a single flat row of tabs.
- `src/functions/renderFormkitComponentPage.js` — used by FormKit components. It already had a `renderGroupedNav()` (opt-in via a `hasSubNav` flag) that renders the primary-tabs-plus-sub-tabs layout.

Because dialog is a standalone component, it inherited the flat nav from `renderComponentPage.js` and had no way to opt into the grouped layout. The grouped-nav logic lived only in the FormKit base class, so there was no shared path for a standalone component to adopt it.

## The Fix

**Shared base class (`src/functions/renderComponentPage.js`, +74 lines).** Added an opt-in grouped nav that mirrors the FormKit implementation:

- New constructor flags, all defaulting to `false`: `hasSubNav`, `hasGettingStarted`, `hasCustomize`, `hasDesign`, `hasKeyboardBehavior`, `hasVoiceover`.
- `renderNav()` early-returns `this.renderGroupedNav()` when `hasSubNav` is set; otherwise it falls through to the existing flat nav unchanged.
- New `renderGroupedNav()` ported from `renderFormkitComponentPage.js`, but using the component's own `auro-<name>` GitHub/npm/source URLs instead of the FormKit monorepo URLs. Primary tabs: **Overview · Code · Design · Accessibility · Releases**; the Code and Accessibility tabs reveal contextual sub-tab rows (Getting Started / Customize / API, and Keyboard Behavior / VoiceOver / Aria) based on the current path.

**Dialog page files (`src/content/dynamic/dialog/`).** Each page sets the FormKit flag block (`hasSubNav = true`, plus the `has*` facet flags, `hasInstall = false`) and imports its per-topic demo markdown:

- Updated `component.js` (Overview), `api.js`, `releases.js`.
- Added `getting-started.js`, `customize.js`, `design.js`, `accessibility.js`, `keyboard-behavior.js`, `voiceover.js`.
- Deleted the dead `nav.js`.
- `api.js` is **markdown-only** (its `initExamples` import was removed) because the published `auro-dialog@4.2.1` demo does not ship an `api.min.js` — its package `exports` map resolves `demo/api.js` → `demo/api.min.js`, which doesn't exist. This matches FormKit's own markdown-only `combobox/api.js`. Pages whose demos do ship a `*.min.js` (Overview, Customize, Design, Accessibility) still call `initExamples`.

**Routing (`src/App.js`).** Added imports and `<Route>` entries for the six new dialog sub-pages and removed the old `install` import/route (the grouped nav has no Install tab).

**Dependencies (`package.json`).** Bumped `@aurodesignsystem/auro-dialog` `^4.2.0` → `^4.2.1`, pinned `@aurodesignsystem/design-tokens` `9.3.2` → `9.3.3`, and relaxed `engines.node` `>=22` → `>=20`. The design-tokens version is intentionally caret-free: the site's `check-dependencies` build step fails if that dependency carries a caret.

## Why This Works

- **Opt-in by default.** The grouped nav only activates when a page sets `hasSubNav`. Every other standalone component page leaves the flag at its `false` default and renders exactly as before, so the change is isolated to dialog and carries no regression risk for the rest of the site.
- **Faithful mirror, not a fork.** `renderGroupedNav()` reproduces the FormKit tabs, labels, and order verbatim; only the source URLs differ (pointing at the standalone `auro-dialog` repo/package instead of the FormKit monorepo). This satisfies the ticket's "matching tabs, labels, and order" requirement without duplicating divergent behavior.
- **Respecting the published package contract.** Making `api.js` markdown-only reflects what `auro-dialog@4.2.1` actually ships. An earlier approach that assumed a pre-release `.tgz` (which did include `api.min.js`) broke against the published artifact; keying off the real `exports` map and shipped files is what makes the page resolve.
- **Green build.** `npm run build` passes end-to-end (check-dependencies + Vite), confirming all imports resolve against the installed `4.2.1` and that the dialog demo assets bundle.

## Outcome

The dialog documentation now browses just like the FormKit component pages: a single row of primary tabs with contextual sub-tabs, in the same order and with the same labels. The documentation site builds successfully with the updated dialog reference and aligned token dependency, and the rest of the component pages are unchanged. Final visual confirmation of the dialog pages' interactive examples in a browser is still recommended before merge (see Ticket Completeness).

## Learnings

- A shared base class can gain a new nav style safely by making it **opt-in via a flag** (`hasSubNav`) rather than branching on component name — the blast radius stays limited to pages that opt in.
- **The published package is the contract.** A component's `exports` map plus the files it actually ships determine what the docs site can import. `auro-dialog@4.2.1` maps `demo/*.js` → `demo/*.min.js` but ships no `api.min.js`, so that page must be markdown-only. Do not assume a pre-release `.tgz` matches the published artifact.
- The docs build's `check-dependencies` step requires `@aurodesignsystem/design-tokens` to be pinned **without a caret**; a caret there fails the build.
- Bugs that appear only in the docs-site integration (and not on the component's own localhost) frequently trace to integration/environment breakage — a missing `dist/`, a bad import — rather than to the component itself.
- Never run `npm run build` from a shell whose working directory has drifted into an installed dependency; it can trigger that package's own build (`auro build`), which wipes its `dist/` and cannot regenerate it from an installed (source-less) package.

## Iterations That Didn't Work

- **A brand-new "flat modern" nav standard.** The first attempt introduced a new shared `componentNav` component with seven flat, semantic nav-links (Overview, Getting Started, Customize, API, Design, Accessibility, Releases) driven by design research. It was scrapped in favor of mirroring the existing FormKit grouped nav exactly, per the ticket's "match FormKit" requirement. The related debate over how to structure accessibility content (one flat page vs. stitching three fragments vs. a sub-nav) was resolved the same way: keep FormKit as-is and mirror it.
- **Linking a pre-release `.tgz` for the dialog demo.** During development the dialog package was linked from a local `0.0.0` tarball that did include `api.min.js`, so `api.js` initially imported `initExamples`. The published `4.2.1` dropped `api.min.js`, forcing the page to become markdown-only.
- **An accidental build inside the installed package.** A shell whose cwd had drifted into `node_modules/@aurodesignsystem/auro-dialog` ran `npm run build`, which executed the component's own `auro build`, wiped its `dist/`, and could not regenerate it (no `src/` in an installed package) — breaking module resolution until the package was reinstalled.
- **A full revert to isolate two reported bugs.** After examples-not-rendering and an unexpected focus-opens-the-dialog behavior were observed, the changes were reverted and then re-implemented cleanly to test whether the bugs persisted. Current hypothesis: both were side effects of the broken `dist/` and the `api.min.js` resolve error, both since fixed; visual confirmation is still outstanding.
